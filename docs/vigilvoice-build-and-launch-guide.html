Quick orientation

What VigilVoice does

VigilVoice checks a voice recording for usable speech and synthetic-speech signals before a sensitive action is allowed to continue. The voice result never approves a transfer by itself. A separate verifier must review the exact recipient and amount and provide a one-time code.

What is real

  • Silero voice activity detection
  • Wav2Vec2 XLSR spoof-classifier inference
  • ONNX Runtime CPU execution
  • Quality gates and risk policy
  • Authenticated sessions and database records
  • OTP/action binding, expiry and audit trail

What is simulated

  • The bank/payment transfer
  • OTP delivery through the local verifier inbox
  • The verifier role on one local machine

What was not done

  • No model was trained by our team
  • No production accuracy claim
  • No real SMS, bank or identity integration
The team contribution: connecting real model inference to a controlled action workflow that fails safely, verifies exact details, consumes approvals once, and records evidence.

Architecture

How the parts work together

1. Browser interface

Native HTML, CSS and JavaScript. It accepts an existing WAV or records up to 10 seconds from the microphone, converts it to 16 kHz mono PCM WAV, previews it, and submits it only after the user clicks Analyze.

2. FastAPI backend

Creates private sessions, validates input, runs audio inference away from the event loop, applies the policy, owns actions and exposes the verifier/audit endpoints.

3. Audio pipeline

Silero finds speech and supports duration/quality evidence. Wav2Vec2 outputs a synthetic-speech score. Smoothing slows recovery while a high raw score escalates immediately.

4. Policy and action gate

LOW or ELEVATED evidence may request verification. HIGH, poor, insufficient, stale, invalid or unavailable evidence prevents completion.

5. PostgreSQL

Stores sessions, risk evaluations, immutable action details, verification challenges, hashed approval tokens and chronological audit events.

6. Local verifier

A separate page requires a verifier key and shows the exact recipient, amount and single-use code. It demonstrates the intended boundary but is not real independent delivery.

Decision logic

What happens to each recording

1
Validate the file. Uploads must be uncompressed, mono, 16 kHz, 16-bit PCM WAV, no more than 30 seconds. Browser recordings are capped at 10 seconds.
2
Check evidence quality. The system measures speech duration, clipping, loudness and an estimated signal-to-noise ratio. It does not invent a safe score when evidence is unusable.
3
Run spoof inference. The local ONNX classifier returns a score used by fixed policy thresholds. The score is a model signal, not a probability that a person is fraudulent.
4
Assign a risk state.
StateMeaningAction behavior
LOWNo strong synthetic signal under current settingsCan request separate verification
ELEVATEDSome spoof signal detectedCan request verification with a warning
HIGHStrong spoof signalTransfer is blocked
POOR QUALITYClipped, quiet or degraded audioAsk for better evidence; block
INSUFFICIENTToo little usable speechAsk for longer speech; block
UNAVAILABLEMissing/stale evidence or model failureFail closed; block
Current thresholds are exploratory. They are kept configurable for later calibration, but the running profile is deliberately labelled uncalibrated.

Launch guide

Start the prototype on Windows

Prerequisites

  • Docker Desktop is installed and running.
  • Python is available for the setup helper.
  • Chrome or Edge is recommended for microphone recording.
  • The first model download needs internet. Normal inference is local afterward.
1
Open PowerShell in the project folder.
cd "C:\Users\Aryamann Sharma\Documents\Claude Code Workspace\SIH"
2
Download the pinned models and demo WAVs if the models folder is empty.
python scripts/fetch_models.py --samples

Approximately 358 MB. Existing correct files are checksum-verified and reused.

3
Create local demo secrets and database settings.
python scripts/configure_demo.py

This creates the ignored .env file without printing secrets.

4
Build and start the backend and database.
docker compose up -d --build
5
Confirm both containers are running.
docker compose ps Invoke-RestMethod http://127.0.0.1:8000/healthz

You should see vigilvoice_backend, a healthy vigilvoice_db, and a health response with "status":"ok".

Demonstration

Run the complete workflow

  1. At the dashboard, choose models/demo/genuine.wav and click Analyze recording. You may also record 3–10 seconds with the microphone.
  2. Read the risk, spoof score, speech duration, signal/noise estimate and reason codes. LOW and ELEVATED still require verification.
  3. Enter a recipient and whole-INR amount. Click Prepare protected transfer. The details become fixed to the generated Action ID.
  4. Click Request verification code. Open the verifier page in another tab.
  5. Enter the verifier key from .env and paste the Action ID. Check the recipient and amount before sharing the six-digit code.
  6. Enter the code on the dashboard and click Complete simulated transfer. The backend rechecks that audio evidence is still safe and fresh, then consumes the approval once.
  7. Review the audit events: action created, challenge issued, OTP verified and action completed.
  8. Choose New transfer, analyze models/demo/synthetic.wav, and show that HIGH evidence blocks the action.

Time limits

  • File evidence: 120 seconds
  • Live stream evidence: 5 seconds
  • OTP: 60 seconds
  • Approval: 60 seconds
  • Wrong OTP attempts: maximum 3

Presenting alone

After requesting a code, run:

python scripts/demo_inbox.py <action-id>

This avoids displaying the long verifier key. It still represents simulated local delivery.

A silent 30-second fallback is available at docs/vigilvoice-teacher-walkthrough.mp4. The seven-slide deck is docs/teacher-presentation.pdf.

Troubleshooting

If the prototype does not launch

ProblemCheck or fix
Docker command failsOpen Docker Desktop, wait for it to finish starting, then rerun docker compose up -d --build.
Models unavailableRun python scripts/fetch_models.py --samples, then restart the backend.
Port 8000 unavailableCheck docker compose ps. Stop another local service using the port or stop the old VigilVoice stack.
Backend exitsRead recent logs with docker compose logs --tail 100 backend.
Database is unhealthyRead docker compose logs --tail 100 db. Do not delete its volume while preserving data matters.
Microphone button disabledUse Chrome/Edge on localhost, allow microphone permission, or use a bundled WAV.
Audio rejectedUse 16 kHz mono 16-bit PCM WAV. Record clear uninterrupted speech or use the known demo files.
Evidence/code expiredAnalyze again and create a new transfer. Expired or locked challenges cannot be reset.

Useful commands

docker compose ps docker compose logs --tail 100 backend docker compose restart backend python -m pytest -q node tests/ui_smoke.cjs node tests/microphone_smoke.cjs

Stop the application

docker compose down

This stops the containers and preserves PostgreSQL data in its Docker volume. The current application is local-only and binds its ports to 127.0.0.1.

Current status

Is this an MVP?

Yes, for a supervised classroom or judging demonstration. It has a complete input-to-decision flow, real inference, failure handling, verification, audit evidence, reproducible launch instructions and measured limitations.

Ready now

  • Local Docker launch
  • WAV and microphone input
  • Real pretrained model execution
  • Quality and spoof policy
  • Protected simulated action
  • Verification and audit trail
  • Slides, guide and fallback video

Needed before real users

  • Consented Indian-language/phone/replay data
  • Representative threshold calibration
  • Fine-tuning if evaluation justifies it
  • Real trusted OTP delivery
  • User accounts and HTTPS deployment
  • Audio retention policy
  • Load and field testing

Recommended next order

  1. Rehearse the current demonstration with the real laptop microphone.
  2. Collect and label target-domain audio with consent.
  3. Evaluate with speaker/source-separated validation and untouched test sets.
  4. Choose an acceptable missed-attack versus false-block tradeoff.
  5. Only then consider fine-tuning, real verification delivery and a wider pilot.
Presentation wording: “We built a working guarded prototype using pretrained models and measured it on a small public set.” Do not say the team trained the detector or that its real-world accuracy is established.
